## 1. Independent ground truth: leaky-repo

[leaky-repo](https://github.com/Plazmaz/leaky-repo) is a third-party
benchmark: 44 files of realistic leaked configuration (dotfiles, FTP and DB
client configs, WordPress, Rails, Django, .env, private keys) with per-file
line counts labeled by its author. It was not used to build secretscan.
`bench/leaky_repo.py` scores it with leaky-repo's own method: per-file counts
of distinct reported lines; reporting more lines than labeled counts as false
positives. "Official" counts risk + informative lines (as leaky-repo's
`benchmark.py` does); "risk-only" counts only credentials, keys and hashes.

**Run 1, before any change informed by leaky-repo** (the only fully
independent measurement):

| Tool | Official: finds (coverage) | Official FPs | Risk-only: finds (coverage) | Risk-only FPs | Files with findings (risk) |
|---|---|---|---|---|---|
| secretscan | 38/175 (21.7%) | 1 | 36/96 (37.5%) | 3 | 26/42 |
| gitleaks | 22/175 (12.6%) | 0 | 21/96 (21.9%) | 1 | 13/42 |
| detect-secrets | 39/175 (22.3%) | 1 | 37/96 (38.5%) | 1 | 23/42 |

**Run 2, after adding rules for the format gaps run 1 exposed.** From this
point leaky-repo is no longer independent for secretscan: the new rules target
formats (unquoted passwords in env/INI/YAML, WordPress `define()`, Django
`SECRET_KEY`, Laravel `APP_KEY`, Rails `master.key`, XML password
attributes and elements, `.netrc`, `/etc/shadow`, Firefox `logins.json`), not
individual files, and corpus noise and the labeled sets were re-checked
afterwards (section 2). Treat run 2 as a description of current coverage, not
as proof.

| Tool | Official: finds (coverage) | Official FPs | Risk-only: finds (coverage) | Risk-only FPs | Files with findings (risk) |
|---|---|---|---|---|---|
| secretscan | 68/175 (38.9%) | 2 | 66/96 (68.8%) | 4 | 38/42 |
| gitleaks | 22/175 (12.6%) | 0 | 21/96 (21.9%) | 1 | 13/42 |
| detect-secrets | 39/175 (22.3%) | 1 | 37/96 (38.5%) | 1 | 23/42 |

Coverage is low for every tool because leaky-repo labels many lines that a
pre-commit scanner deliberately doesn't report. secretscan still misses
**30 of 96 risk lines**:

| Missed | Lines | Why |
|---|---|---|
| `db/dump.sql` bcrypt hashes | 10 | by design: password hashes are not reported |
| `.mozilla/firefox/logins.json` | 3 of 8 | encrypted fields; the file itself is reported |
| `.bash_profile` | 3 of 6 | placeholders (`dummy-pass`, `sampleHerokuKey`) and a fake key ID without the AKIA prefix |
| `web/var/www/.env` | 2 of 6 | all 4 lines the file marks `# Risk` are found; the CSV counts 2 more |
| `filezilla/filezilla.xml` | 2 | `<Pass>ExamplePas123</Pass>`: value contains the placeholder word "Example" |
| `.esmtprc` | 2 | `password "password"`: literal placeholder word |
| `db/robomongo.json` | 2 of 3 | dictionary-style values (`mongopass`, `roboMongoSSHPass`) dropped as placeholder-like |
| `deployment-config.json`, `.ftpconfig`, `filezilla/recentservers.xml` | 4 | usernames/hosts labeled as risk, values without a credential key |
| `web/var/www/public_html/wp-config.php` | 1 of 9 | `DB_PASSWORD` is `'admin'`, treated as a placeholder word |
| `web/js/salesforce.js` | 1 | password passed as a positional function argument |

The false positives counted by the method are mostly double counting: a
credential file is reported once as a file (`sensitive-file`, line 0) and
again for the secret on its line (`.netrc`, `id_rsa`, `.ppk`).

## 3. Manual adjudication of every corpus finding

"Findings per 1k package files" above counts everything reported. Every one
of the 132 secretscan findings on the 44,284 corpus files was inspected and
labeled (`bench/corpus_labels.tsv`, applied by `bench/adjudicate.py`, which
fails on any unlabeled finding):

```
44284 files, 132 findings

| Label | Findings | Per 1k files |
|---|---|---|
| live-credential | 0 | 0.00 |
| example-credential | 116 | 2.62 |
| not-a-secret | 16 | 0.36 |

not-a-secret:
    8  generic-api-key          JS identifiers in compiled bundles and source maps
    2  generic-api-key          config option name
    2  generic-api-key          SHA-1 cache keys of credentials, not credentials
    1  generic-api-key          encoding name in a service model
    1  gcp-service-account-key  placeholder private_key_id in a test account file
    1  generic-api-key          HTTP header name
    1  generic-api-key          function name in a source map

example-credential:
   58  private-key              PEM private keys in docs and test fixtures (some truncated with ...)
   10  password-assignment      passwords and keys in API examples and unit tests
    9  aws-session-token        AWS documentation example session tokens (contain EXAMPLE)
    8  jwt                      test tokens
    7  generic-api-key          passwords and keys in API examples and unit tests
    6  generic-api-key          customer-supplied encryption keys in tests
    6  url-credentials          user:password URLs in docstrings and URL-parsing tests
    5  password-assignment      passwords in documentation examples
    4  azure-sas-token          SAS signature in SDK samples
    2  generic-api-key          refresh token in a kubeconfig test
```

So the genuine false-positive rate on package code is **0.36 per 1,000
files**; the rest is credential material that packages ship as examples
(private keys in test fixtures, documented passwords, sample SAS tokens),
which secretscan reports on purpose. gitleaks' and detect-secrets' corpus
findings were **not** adjudicated, so their noise column is not directly
comparable to this split.

## 4. False negatives of the noise filters, per alphabet

`TestFalseNegativesPerAlphabet` (run in CI) puts 20,000 random values per
alphabet into `api_secret = "..."` and records why any are lost. "Removed by
filters" is the cost of noise reduction; "below entropy threshold" is a rule
design limit (very low-entropy random strings).

| Alphabet | Removed by filters | Below entropy threshold | Filter reasons |
|---|---|---|---|
| alnum 16-45          | 0.000% | 0.030% | map[] |
| hex 32/40/64         | 0.000% | 0.005% | map[] |
| HEX upper 32         | 0.000% | 0.010% | map[] |
| base64 std           | 0.000% | 0.000% | map[] |
| base64url            | 0.000% | 0.000% | map[] |
| base32 lower 52      | 0.000% | 0.000% | map[] |
| base32 upper 32      | 0.000% | 0.005% | map[] |
| password 12-24       | 0.015% | 0.165% | map[digit-free-name-or-path:1 word-like:2] |
| lower+digits 20-40   | 0.010% | 0.300% | map[identifier:2] |

Known gaps, by design or not yet handled: passphrases made only of dictionary
words under a generic key (`api_secret = "CorrectHorseBatteryStaple"`),
UUID-shaped secrets without a provider rule, literal placeholder words used
as real passwords (`password = "password"`), password hashes, and values
below a rule's entropy threshold. Each is pinned as a "borderline" case in
`internal/detect/filters_test.go`.

## Reproduce

```sh
bench/fetch-corpus.sh                       # pinned package versions + generated sets
python3 bench/precision.py                  # section 2
python3 bench/adjudicate.py                 # section 3
git clone https://github.com/Plazmaz/leaky-repo /tmp/leaky-repo
git -C /tmp/leaky-repo checkout 2e95135
python3 bench/leaky_repo.py /tmp/leaky-repo # section 1
go test ./internal/detect -run PerAlphabet -v   # section 4
```

Independent reproductions are very welcome, especially on private code:
`secretscan dir . -f stats` prints counts only (no paths, values or
fingerprints) and can be pasted into an issue.
